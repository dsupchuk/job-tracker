# Deployment

Everything in the repository is ready to deploy. What remains is creating three
accounts and pasting values between their dashboards — steps that need your
credentials, so they are yours to do.

Read this top to bottom once before starting: the three services reference each
other, and doing them out of order means going back.

---

## What goes where

| Piece | Service | Config in this repo |
|---|---|---|
| PostgreSQL | Neon | — (connection string is an env var) |
| Backend | Render | `render.yaml`, `docker/backend.Dockerfile` |
| Frontend | Vercel | `frontend/vercel.json` |

---

## 1. Database — Neon

1. Create a project. Any region will do, but putting it near the Render region
   (`frankfurt` in `render.yaml`) saves a round trip on every query.
2. Copy the connection string. It looks like:

   ```
   postgresql://user:password@ep-something.eu-central-1.aws.neon.tech/neondb?sslmode=require
   ```

3. **Convert it to a JDBC URL**, which is what Spring wants, and split out the
   credentials:

   ```
   SPRING_DATASOURCE_URL=jdbc:postgresql://ep-something.eu-central-1.aws.neon.tech/neondb?sslmode=require
   SPRING_DATASOURCE_USERNAME=user
   SPRING_DATASOURCE_PASSWORD=password
   ```

   Keep `?sslmode=require` — Neon refuses plaintext connections, and the failure
   reads as a generic connection error rather than anything about TLS.

Flyway creates the schema on first boot. There is nothing to run by hand.

---

## 2. Backend — Render

1. New → Blueprint, point it at this repository. Render reads `render.yaml`.
2. Fill in the variables it marks as required:

   | Variable | Value |
   |---|---|
   | `SPRING_DATASOURCE_URL` | from Neon, JDBC form |
   | `SPRING_DATASOURCE_USERNAME` | from Neon |
   | `SPRING_DATASOURCE_PASSWORD` | from Neon |
   | `APP_CORS_ALLOWED_ORIGINS` | the Vercel URL — you will not have it yet, see step 4 |

   `JWT_SECRET` is generated by Render. Do not set it by hand, and know that
   changing it later signs every existing session out.

3. Deploy. Render polls `/actuator/health` and will not route traffic until it
   answers. First boot takes around 15 seconds once the image is built.

Check it: `https://<your-api>.onrender.com/actuator/health` should return
`{"status":"UP"}`. Nothing else under `/actuator` is exposed.

> The free plan sleeps after inactivity, so the first request to a cold demo
> takes ~30 seconds. Worth mentioning next to the demo link rather than letting
> a visitor conclude the app is broken.

---

## 3. Frontend — Vercel

1. New Project → import the repository.
2. Set the root directory to `frontend`. Vercel reads `vercel.json` from there
   and needs no further build configuration.
3. Add one environment variable:

   ```
   VITE_API_URL=https://<your-api>.onrender.com
   ```

   It is read at **build** time, so changing it later needs a redeploy, not just
   a restart.

`vercel.json` rewrites everything except `/assets/*` to `index.html`, so
client-side routes survive a hard refresh — without it, opening `/board`
directly returns a 404 from the CDN.

---

## 4. Close the CORS loop

Go back to Render and set `APP_CORS_ALLOWED_ORIGINS` to the Vercel URL
(`https://job-tracker.vercel.app`, or whatever Vercel assigned), then redeploy.

Until you do, the browser blocks every request and the app shows "Cannot reach
the server" — which looks like the backend is down when it is only being
disallowed. If you use a custom domain as well, list both, comma-separated.

Verify end to end: open the site, press **Try the demo**, and confirm the table
fills in.

---

## 5. The demo account

`render.yaml` already sets:

- `APP_DEMO_SEED=true` — creates `demo@demo.com` / `demo` with ~20 sample
  applications on first boot. Idempotent; a redeploy will not duplicate them.
- `APP_DEMO_RESET_CRON=0 0 3 * * *` — deletes and recreates the account nightly
  at 03:00 UTC, so whatever visitors do to it does not accumulate. Applications
  and their status history go with the user by cascade.

Both are covered by `DemoDataTest`, because a scheduled job that only runs at
03:00 is not something you want to be testing in production.

A private deployment of the same image just leaves `APP_DEMO_SEED` unset.

## Environment variables, in full

| Variable | Required | Default | Notes |
|---|---|---|---|
| `SPRING_PROFILES_ACTIVE` | yes | `dev` | `prod` in deployment |
| `SPRING_DATASOURCE_URL` | yes | local Postgres on 5433 | JDBC form, keep `sslmode=require` |
| `SPRING_DATASOURCE_USERNAME` | yes | `jobtracker` | |
| `SPRING_DATASOURCE_PASSWORD` | yes | `jobtracker` | |
| `JWT_SECRET` | yes | a dev-only value | ≥ 32 bytes; rotating it ends all sessions |
| `APP_CORS_ALLOWED_ORIGINS` | yes | `http://localhost:5173` | comma-separated |
| `APP_DEMO_SEED` | no | `false` | `true` for the public demo |
| `APP_DEMO_RESET_CRON` | no | unset | Spring cron, six fields, UTC |
| `PORT` | no | `8080` | the platform usually sets this itself |
| `VITE_API_URL` | yes (frontend) | — | build-time; redeploy after changing |

## Verified locally

The image was built and run with production settings against a separate
database before any of this was written down:

- `/actuator/health` → `{"status":"UP"}`, reachable without a token
- `/actuator/env` → 401, so the rest of actuator stays shut
- demo seeding on the `prod` profile → 20 applications, login works
- CORS → the configured origin is allowed, an unknown origin gets 403

What could not be verified without your accounts: that Neon accepts the
connection string, and that Render's and Vercel's own build pipelines complete.
